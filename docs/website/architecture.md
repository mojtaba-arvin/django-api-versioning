# Documentation website architecture

## Status

This document defines repository boundaries and the implementation contract. It does not claim that the Astro website has been implemented or that a deployable `dist/` exists yet.

## Source-of-truth map

| Concern | Canonical location | Rule |
| --- | --- | --- |
| Python implementation | `django_api_versioning/` | The only runtime package distributed on PyPI |
| Package unit tests | `tests/` | Keep package regression tests here |
| Django integration scenarios | `integration_test_project/` | Reuse the existing project; extend it for executable evidence |
| Long-form articles | `docs/articles/` | Existing 25 Markdown files are the canonical corpus |
| Reference contract | `docs/reference/versioning-contract.md` | Preserve as package reference |
| Website application | `website/` | Astro app, Node dependencies, pages, components, assets |
| Website architecture and handoff | `docs/website/` | Maintainer-authored project contract |
| Generated website data | `website/src/data/generated/` | Derived from a pinned source commit; never hand-edited |

## Runtime and build boundaries

The website is a static presentation layer. Python/Django tooling runs during development or CI to inspect the package and produce evidence. Astro consumes the resulting data and Markdown content at build time.

There must be no runtime dependency on Netlify, serverless functions, a database, or a Python process. Netlify and GitHub Pages are deployment targets, not architectural dependencies.

The Astro project root is `website/`. The final output is `website/dist/`. GitHub Pages base-path handling must be configurable; a custom domain must not require a different content architecture.

## Articles

The 25 existing Markdown articles live in `docs/articles/`. They must remain in that location as the single tracked source. The website should load or stage them during its build without committing a second editable copy.

Do not fetch the moving `main` branch at build time. The site build must use the articles present in the same checked-out repository revision as the website code. Article metadata/slug collisions must be handled by stable file identity, not by assuming frontmatter slugs are unique.

## Evidence lifecycle

Evidence is generated by executable scenarios in or under the existing `integration_test_project/`. The generator must inspect the package source from a single immutable Git commit and read the version from the repository metadata. It must not combine:
- package code from one commit;
- a PyPI wheel from another version;
- article examples from an unrelated revision;
- old output files from the previous Agent run.

Each generated evidence snapshot should carry provenance, including the full commit SHA, package version, runtime versions, scenario identifiers, and hashes where appropriate. A check mode should fail when committed generated data is stale.

The Netlify Agent log contains a useful Segment Lab design and scenario inventory, but its concrete run was pinned to package 0.3.5 at commit `e5a5466ac0fab1eb1ef41d8d570ccac1301f2cd9`. It is a design/reference input only until each scenario and source locator is rerun against the chosen current baseline. Its generated `routes.json` and `tools/README.md` contents were not present in the captured log and must not be reconstructed by guessing.

## PyPI packaging

The website, article corpus, and integration project are repository assets, not part of the runtime package. The package-discovery allowlist in `pyproject.toml` limits discovered Python packages to `django_api_versioning*`. `MANIFEST.in` explicitly prunes website, docs, and integration-project trees from the sdist.

Every release check must inspect the actual wheel and sdist file lists. A packaging configuration is not a substitute for artifact verification.

## Homepage content contract

The homepage has ten planned sections, in this order:

1. What it is, with installation.
2. The API-versioning problem.
3. A real `@endpoint` example.
4. Actual `check_versions` output.
5. Segment Point and forward-inheritance diagram.
6. Registration time versus request time.
7. Verified capabilities.
8. DRF boundaries.
9. Known limitations.
10. Quick Start and useful links.

The diagram must show only concepts already introduced in the real examples and capabilities sections. It must be labelled as an explanatory visualization, not actual Python execution, and must have a no-JavaScript fallback.

## Interaction and accessibility contract

Planned interactions: Segment Explorer, code copy, content search, dark/light theme, reading progress, heading anchors, version/provenance information, mobile navigation, and reduced-motion support.

Target WCAG 2.2 AA. Keyboard operation, visible focus, semantic structure, reduced-motion preferences, and stable layout (CLS target 0) are required. Motion should clarify the request path rather than decorate it.

## Deployment contract

For a future Netlify site:
- Base directory: `website`
- Build command: `npm run build`
- Publish directory: `dist` (relative to `website`)

For GitHub Pages, use a GitHub Actions workflow to build `website/` and publish only `website/dist/`. The workflow must set the appropriate Astro base path for a project site, and must not alter Python package release workflows.
