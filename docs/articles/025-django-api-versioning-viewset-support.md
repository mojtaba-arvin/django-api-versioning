# Versioned DRF ViewSets with Route-Level Inheritance

Django REST Framework already provides the standard machinery for ViewSet routing: list and detail routes, lookup handling, and custom routes declared with `@action`. It also provides versioning schemes that expose the requested version through `request.version`.

What it does not decide for your application is which ViewSet implementation should serve each API version. You can write that dispatch logic yourself, but then you must also preserve DRF's generated route metadata, action mappings, URL reversal, and schema introspection.

Django API Versioning adds an optional `VersionedRouter` that delegates route generation to DRF's `SimpleRouter`, then registers each generated Django `URLPattern` in the package's version registry. This gives DRF applications the same route-level inheritance model already available through the package's `@endpoint` decorator.

## 1. Configure the DRF versioning adapter

Install a DRF version compatible with your Django release. The package keeps DRF optional:

```bash
# Django 4.2 compatibility
pip install "djangorestframework>=3.17.2,<3.18"

# Django 5.2, 6.0, or 6.1
pip install "djangorestframework>=3.18.3,<3.19"
```

Configure the versioning adapter before importing your ViewSet modules:

```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_VERSIONING_CLASS": (
        "django_api_versioning.routers.VersionedRouterVersioning"
    ),
}
```

You can also set `versioning_class = VersionedRouterVersioning` on individual ViewSets if you do not want to change the project-wide DRF default.

The adapter reads the version namespace generated by `VersionedRouter` and exposes the numeric version as a string through `request.version`: `"1"`, `"2"`, and so on. The `v` prefix is part of the URL namespace, not the value returned by `request.version`.

## 2. Register ViewSets

Use the familiar DRF registration style, adding the package's `version` argument:

```python
# project/urls.py
from django_api_versioning.routers import VersionedRouter
from orders.views import OrderViewSetV1, OrderViewSetV2

router = VersionedRouter()

router.register(
    "orders",
    OrderViewSetV1,
    version=1,
    basename="order",
)
router.register(
    "orders",
    OrderViewSetV2,
    version=2,
    basename="order",
)

urlpatterns = router.urls
```

With `API_MAX_VERSION = 3`, the router generates:

- `/api/v1/orders/` using the V1 ViewSet;
- `/api/v2/orders/` using the V2 ViewSet where it replaces V1 routes;
- `/api/v3/orders/` using the latest applicable declarations.

Always pass the same explicit `basename` across versions. The router rejects a basename change for the same prefix and rejects duplicate basenames across different prefixes in one router instance. This keeps generated URL names stable and reversible.

## 3. Inheritance happens per route

The important distinction is that the router does not replace an entire ViewSet route set when a newer class is registered. It replaces matching generated routes independently.

Imagine that V1 defines:

- `list`;
- `retrieve`;
- a custom `publish` action.

V2 changes `list` and `retrieve`, but does not redeclare `publish`.

The result is:

| Concrete version | list | retrieve | publish |
| --- | --- | --- | --- |
| v1 | V1 | V1 | V1 |
| v2 | V2 | V2 | V1 inherited |
| v3 | V2 inherited | V2 inherited | V1 inherited |

This is the useful property for long-lived APIs: a developer declares only the routes whose implementation changes. An unchanged custom action does not disappear merely because the newer ViewSet class does not repeat it.

This is route inheritance, not automatic serializer or response compatibility. If V1's action is still inherited into v2, it still uses the V1 callback and its associated DRF configuration. Review that behavior as part of your API contract.

### Explicit version sets

Some routes should exist only in selected versions:

```python
router.register(
    "exports",
    ExportViewSet,
    versions=[1, 3],
    basename="export",
)
```

The export route exists in v1 and v3. It is not registered in v2, so v2 requests return 404. The router does not silently fall forward to another version.

## 4. DRF actions, reversal, and hyperlinks

The router preserves the URL patterns and callbacks generated by DRF. That includes standard list/detail mappings, custom `@action` methods, action-level kwargs, lookup regexes or path converters, and the configured trailing-slash policy.

The `VersionedRouterVersioning` adapter keeps reverse operations in the active version namespace:

- `ViewSet.reverse_action()` reverses against the current version;
- `HyperlinkedIdentityField` generates links under the current version;
- `HyperlinkedRelatedField` can validate links against the current version;
- nested application namespaces are preserved.

For package-level reversal, use `api_reverse()` with an explicit version:

```python
from django_api_versioning import api_reverse

url = api_reverse("order-list", version=2)
```

This returns the registered route path under Django's script prefix. It is package-relative and does not add an outer URL namespace. DRF's versioning adapter handles namespaced reversal for ViewSets and hyperlinked serializers.

The reversal helper supports both DRF's default regex-backed routes and path-converter routes. Duplicate route names within the same concrete version fail instead of silently selecting an arbitrary match.

## 5. Router options and namespaces

The constructor retains the useful `SimpleRouter` options:

```python
router = VersionedRouter(
    trailing_slash=False,
    use_regex_path=False,
)
```

Set `use_regex_path=False` when you want Django path converters, including custom converters, rather than DRF's default regex lookup patterns.

Each concrete version is placed under a Django namespace named `vN`. If you mount multiple router instances in one URLconf, include each under a distinct outer namespace:

```python
from django.urls import include, path

urlpatterns = [
    path(
        "",
        include((orders_router.urls, "orders"), namespace="orders"),
    ),
    path(
        "",
        include((billing_router.urls, "billing"), namespace="billing"),
    ),
]
```

The versioning adapter preserves the complete namespace chain, for example `orders:v2`, when reversing a route.

## 6. Lifecycle middleware and nested URL includes

The physical route still uses `API_BASE_PATH`, which defaults to `api/v{version}/`. If the API is mounted below a parent URL prefix, such as `/internal/api/v2/orders/`, `LifecycleMiddleware` finds the configured API base path at a path-segment boundary.

That means version deprecation and sunset headers continue to work when a versioned router is included below another URL prefix. A lookalike path segment such as `/notapi/v2/` is not treated as the configured API base path.

## 7. What this integration does not do

The initial integration deliberately supports DRF `SimpleRouter`, not `DefaultRouter`. It does not claim API-root or format-suffix parity.

It also does not:

- transform serializers or response payloads;
- infer whether a ViewSet implementation is backward-compatible;
- change authentication, permissions, throttling, filtering, pagination, or rendering;
- enable header, query-parameter, host, or tenant-based negotiation;
- remove an inherited route when a later ViewSet omits its action.

In particular, an action declared in V1 remains inherited until it is explicitly replaced. There is not yet a route-removal/tombstone API; that design is tracked in [Issue #39](https://github.com/mojtaba-arvin/django-api-versioning/issues/39).

Header/query/tenant negotiation is also separate. DRF already has parsers for those channels, but dispatching to a version-specific ViewSet after negotiation requires a runtime dispatcher, defined cache behavior, and correct reverse semantics. The package's reserved negotiation settings do not activate those behaviors. See the [product roadmap](https://github.com/mojtaba-arvin/django-api-versioning/issues/36).

## 8. OpenAPI and compatibility checks

The router preserves the metadata schema tools need, but it does not generate or diff OpenAPI documents itself. The planned integration reuses:

- [drf-spectacular](https://drf-spectacular.readthedocs.io/) to generate a schema for each API version;
- [oasdiff](https://github.com/oasdiff/oasdiff) to detect breaking changes between a released schema and a candidate schema.

This work is tracked separately in [Issue #38](https://github.com/mojtaba-arvin/django-api-versioning/issues/38). A route existing in the version matrix is not proof that its request and response contracts remain compatible; semantic schema checks and runtime tests are separate safeguards.

## Summary

Use `@endpoint` for Django-native views and `VersionedRouter` for DRF ViewSets. The router delegates route generation to DRF, while Django API Versioning manages version-specific implementation selection, per-route inheritance, route-matrix visibility, and version-aware reversal. DRF remains responsible for the actual ViewSet behavior and serializer contracts.
