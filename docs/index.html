📊 The Problem & The Solution

You shipped v1 with a string amount. Now the team needs integer cents and currency code. Changing the view breaks every v1 client in production.

Without this package, you maintain one path() per version and copy unchanged views:

# ❌ Manual URL routing (error-prone)
urlpatterns = [
    path("api/v1/orders/", views.order_list_v1),
    path("api/v2/orders/", views.order_list_v2),  # copy/paste
    path("api/v3/orders/", views.order_list_v2),  # remember to add
    # ... × 150 endpoints
]

With Django API Versioning:

# ✅ Declarative versioning
@endpoint("orders/", version=1)
def order_list_v1(request):
    return JsonResponse({"total": "19.99"})

@endpoint("orders/", version=2)
def order_list_v2(request):
    return JsonResponse({"total": 1999, "currency": "USD"})
    # Serves v2, v3, v4... up to API_MAX_VERSION automatically
Why auto-inheritance? The v2 declaration extends forward to every future version until you add another declaration for that route. No manual routing, no forgotten paths.

✨ Key Features

🎯 One-time Setup

Include the registry once. Every @endpoint registers its own routes automatically.

📈 Segment-based Inheritance

Declare v2 once, it serves v2 through the next declaration or API_MAX_VERSION.

🔗 Deterministic URL Reversal

api_reverse() requires explicit version—no silent routing surprises.

🛠️ Works Without DRF

Pure Django function-based and class-based views work as expected.

🔍 Matrix Inspection

check_versions command shows which view serves each version.

📋 CI Guards

assert_version_matrix() detects silent version drift in tests.

🌍 DRF Full Support

APIView, GenericAPIView, ViewSets, routers, custom actions, authentication, permissions.

📭 Deprecation Headers

Automatic Deprecation and Sunset headers for version lifecycle management.

⚡ Why Not Use DRF's Built-in Versioning?

DRF's URLPathVersioning, NamespaceVersioning, AcceptHeaderVersioning, QueryParameterVersioning, and HostNameVersioning all extract the version and set request.version. But they don't decide which view serves which version, and they don't register your URLs.

This package adds the layer DRF deliberately left to you.

🚀 Quick Start

1. Install

pip install django-api-versioning

2. Configure

# settings.py
INSTALLED_APPS = [
    "django_api_versioning",
]

API_BASE_PATH = "api/v{version}/"
API_MIN_VERSION = 1
API_MAX_VERSION = 3

3. Include URLs

# urls.py
from django.urls import include, path
from django_api_versioning.urls import urlpatterns as api_urlpatterns

urlpatterns = [
    path("", include(api_urlpatterns)),
]

4. Decorate Views

from rest_framework.views import APIView
from rest_framework.response import Response
from django_api_versioning.decorators import endpoint

@endpoint("orders//", version=1, view_name="order-detail")
class OrderDetail(APIView):
    def get(self, request, order_id):
        return Response({"id": order_id, "total": "19.99"})

5. That's It!

GET /api/v1/orders/42/  →  {"id": 42, "total": "19.99"}
GET /api/v2/orders/42/  →  {"id": 42, "total": "19.99"}  # Inherited from v1
GET /api/v3/orders/42/  →  {"id": 42, "total": "19.99"}  # Inherited from v1
