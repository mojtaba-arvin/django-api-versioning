# Version-aware DRF router: implementation design

**Status:** Proposed; implementation not started  
**Target API:** `VersionedRouter`  
**Depends on:** DRF's `SimpleRouter`, the package URL registry, and the existing path-version contract  
**Scope:** First-class versioned registration of DRF ViewSets without taking ownership of serializers or response compatibility

## 1. Product problem

The package already lets teams replace an endpoint implementation at a version boundary and inherit unchanged registrations into later versions. However, a project using DRF's conventional `ViewSet` + router workflow cannot register a ViewSet directly. The current registry expects a Django view class or callable, while `ViewSet.as_view()` requires the action map generated by a router.

Manually calling `as_view({"get": "list"})` is not an equivalent solution: it creates one configured route and bypasses router discovery of standard list/detail routes and `@action` methods, including action-level configuration. This is a concrete onboarding gap for DRF applications, not a request to add another version parser.

DRF documents routers as the standard mechanism for generating ViewSet URL patterns and includes custom `@action` routes in that process:
- https://www.django-rest-framework.org/api-guide/routers/
- https://www.django-rest-framework.org/api-guide/viewsets/

DRF's versioning layer already exposes `request.version`, supports URL-path and Accept-header schemes, and integrates version-aware URL reversal. However, DRF explicitly leaves the application-specific behavior change to the developer (for example, manually switching serializers). This package must complement that layer: the package selects the correct ViewSet implementation for a route/version and preserves unchanged route registrations; the adapter exposes the selected version to DRF so serializers, permissions, schema tooling, and application code can use the same value. We must not reimplement DRF's general request-version parser or claim ownership of serializer compatibility.

Reference: https://www.django-rest-framework.org/api-guide/versioning/

## 2. Proposed public API

The initial API should mirror the package's existing `endpoint` semantics while retaining DRF's familiar registration arguments:

```python
from django_api_versioning.routers import VersionedRouter

router = VersionedRouter()

router.register(
    "orders",
    OrderViewSetV1,
    version=1,
    basename="order",
)
router.register(
    "orders",
    OrderViewSetV2,
    version=2,
    basename="order",
)

urlpatterns = router.urls
```

With `API_MAX_VERSION = 3`, the V1 ViewSet supplies the v1 route set; V2 replaces the matching route set from v2 onward. A route added only by V2 exists only where V2 is registered. This is route-set inheritance, not method or serializer inheritance.

Explicit registration should be supported:

```python
router.register(
    "exports",
    ExportViewSet,
    versions=[1, 3],
    basename="export",
)
```

The first release should support the `SimpleRouter` route model, including its standard and dynamic routes. A separate `VersionedDefaultRouter` (including version-aware API-root and format-suffix behavior) must not be implied until its reverse and schema semantics are designed and tested. Do not silently claim DefaultRouter parity.

## 3. Architecture decision

### 3.1 Reuse DRF route generation; do not copy its internals

For each logical registration and each concrete API version in its resolved segment, delegate route generation to DRF's public `SimpleRouter` API. Preserve the resulting Django `URLPattern` and its callback rather than reconstructing a callable from the ViewSet.

This is necessary to retain:
- standard list/detail mappings;
- custom `@action` routes and their method maps;
- action-level `kwargs` such as permission, serializer, throttle, and filter overrides;
- basename, suffix, detail, and other callback metadata used by DRF introspection;
- lookup regex or converter behavior;
- the configured trailing-slash policy.

Do not copy `SimpleRouter.get_urls()` or the route templates into this package. That would couple the package to DRF internals and create a second router implementation that can drift.

### 3.2 Extend the registry to retain complete URLPattern objects

The current `UrlRegistry.register()` constructs patterns using Django `path()`. A DRF router can produce regex-backed patterns as well as path-converter patterns. Rebuilding those patterns from `str(pattern.pattern)` would lose converter and callback metadata.

Add a registry entry point for a complete generated `URLPattern`, with explicit metadata:
- logical endpoint identity (router prefix + basename, independent of version);
- source version (the ViewSet declaration's change point);
- concrete route version;
- generated URL name.

The registry remains the source of truth for generated urlpatterns, version matrices, and collision resolution. Existing `register()` behavior must remain backward-compatible and can delegate to the same internal insertion primitive.

The registry must preserve the existing precedence contract: a higher `source_version` wins for the same concrete route, while equal source versions retain the registry's established last-registration-wins behavior. The ViewSet adapter should detect and report accidental duplicate route declarations where it can do so without changing the decorator API's established semantics. Cross-version replacement follows the existing segment rules.

### 3.3 Preserve route-level inheritance, not all-or-nothing ViewSet replacement

Each generated URL pattern is an independently registered logical endpoint. If a v2 ViewSet replaces the list and detail routes but no longer declares a v1 custom action, that action remains inherited from v1 unless a later declaration explicitly replaces or removes it through a separately designed removal mechanism. A ViewSet registration must not erase unrelated route patterns merely because they came from an earlier ViewSet class. This is essential to the package's core promise: only changed routes need a new declaration.

Derive a stable logical route identity from the router prefix and generated route name (or an equivalent stable route key), excluding the version prefix. The route matrix must group the same list/detail/action route across versions while keeping distinct actions separate.

### 3.4 Generate one DRF route set per ViewSet registration

DRF's `BaseRouter.register()` rejects duplicate basenames within a router instance. Versioned declarations intentionally reuse the same logical basename across versions. Therefore, each versioned declaration must be isolated during DRF route generation, then its patterns merged into the package registry.

Do not make users invent version-suffixed basenames. URL names such as `order-list`, `order-detail`, and `order-archive` should remain stable across versions; `api_reverse(name, version=N)` selects the intended version.

### 3.5 Version prefix and callback metadata

The generated route path must be prefixed with the configured `API_BASE_PATH` for each concrete version. Prefixing must preserve the original `RoutePattern` or `RegexPattern`, converters, and callback attributes. The selected route's version metadata must be available to lifecycle middleware and the optional DRF versioning adapter without guessing from path substrings.

A small adapter may expose the resolved route version as `request.version` for DRF views. It must read the route metadata established by the resolver and must not replace or interfere with DRF authentication, permissions, or content negotiation.

## 4. URL reversal

DRF callbacks use generated names for hyperlinks and `ViewSet.reverse_action()`. Those names must continue to resolve inside a request for the correct concrete version.

The package-level `api_reverse(view_name, version=...)` must support both path-converter and regex-backed patterns. It must select the exact pattern for the requested version and delegate parameter encoding/validation to Django's URL reversing implementation rather than hand-parsing regex strings.

If the same view name is present in multiple versions and no version is supplied, preserve the current explicit ambiguity error. Never select an arbitrary version based on registry order.

URLconf inclusion and namespacing must be tested at two levels: Django's `reverse()` and DRF's `ViewSet.reverse_action()` must resolve the mounted namespaced route using the request context; package-level `api_reverse()` retains its existing package-relative behavior unless a namespace is explicitly supplied by a future API. Do not make the package helper guess the namespace from a global registry.

## 5. Schema and introspection

The generated callbacks must preserve DRF's `cls`, `actions`, `initkwargs`, `basename`, `detail`, `suffix`, and action metadata. Tests must exercise schema generation against the generated router patterns, not merely assert that `resolve()` returns a callable.

### 5.1 First-class schema-tool integration

Do not build a competing OpenAPI generator or a proprietary schema format. Provide a tested integration with `drf-spectacular` as an optional developer dependency/recipe:

- The package's DRF versioning adapter exposes the selected route version as `request.version`.
- `manage.py spectacular --api-version <version>` can generate a schema containing unversioned routes plus the selected API version.
- A `SpectacularAPIView` can use the same versioning adapter or an explicit `api_version` value.
- CI can keep one committed OpenAPI snapshot per supported public API version and use `oasdiff breaking` to detect compatibility regressions between a released version and a candidate. The package should document the integration and provide a reproducible example, but must not bundle oasdiff or claim its breaking-change rules as its own.

This creates a complete workflow: route dispatch defines the versioned implementation, schema generation describes the resulting contract, and an established diff tool guards consumer compatibility.

Version-specific paths should remain independently visible to schema generators. This feature does not promise one merged OpenAPI document with automatic version filtering; that is a separate product contract.

## 6. Compatibility and optional dependency

- DRF remains an optional runtime dependency.
- Importing `django_api_versioning`, `django_api_versioning.urls`, and using Django-native `@endpoint` must not import DRF.
- Importing `django_api_versioning.routers.VersionedRouter` without DRF should raise a clear, actionable optional-dependency error (or use a lazy import boundary); it must not break core package imports.
- Pin the tested DRF/Django combinations to upstream-supported combinations. Do not infer compatibility from a single latest-version CI environment.
- DRF 3.18.x dropped Django 4.2, 5.0, and 5.1; its current 3.18.3 release advertises Django 5.2, 6.0, and 6.1 with Python 3.10–3.15. DRF 3.17.2 is the appropriate upstream line for the package's Django 4.2 compatibility jobs (Python 3.10–3.14). The router feature should test DRF 3.17.2 on the Django 4.2 combinations that upstream supports, and DRF 3.18.3 on the Django 5.2/6.0/6.1 combinations that upstream supports.
- The generic `dev` extra specifies `djangorestframework>=3.18`, while tox now pins the actual compatibility matrix independently: DRF `>=3.17.2,<3.18` for Django 4.2 and DRF `>=3.18,<3.19` for Django 5.2, 6.0, and 6.1 (merged through PR #34). The router integration must use these same upstream-supported combinations and must not infer compatibility from the generic development extra.
- Test the oldest DRF release the project chooses to support and the current supported DRF release on matching Python/Django combinations.

## 7. Explicit non-goals

This feature will not:
- transform serializers or response payloads;
- infer backward compatibility from ViewSet class inheritance;
- choose serializers automatically based on request version;
- alter authentication, permissions, throttling, filtering, pagination, or renderer behavior;
- implement Header/Query negotiation or tenant version policy;
- silently merge multiple versions into one OpenAPI schema.

Applications remain responsible for the API contract implemented by each ViewSet. The package owns route registration, deterministic version dispatch, route introspection, and lifecycle version identification.

## 8. Required tests before implementation is considered complete

1. Two ViewSets registered for the same prefix/basename at v1 and v2; verify v1, v2, and inherited v3 callbacks, including a custom action that exists only in v1 and therefore remains inherited in v2/v3.
2. Explicit `versions=[...]` registration and gaps; missing route remains a 404 rather than falling forward to a different ViewSet.
3. Standard list/detail actions and method maps.
4. List and detail `@action` routes, custom `url_path` / `url_name`, action kwargs, and additional HTTP method mappings.
5. Lookup field, lookup regex, path converter, trailing slash on/off, and malformed lookup behavior.
6. Duplicate basename in different versions is allowed; duplicate logical route in the same version fails deterministically.
7. `api_reverse()` for list, detail, and custom actions in each version, including regex-backed and path-converter routes.
8. `resolve()` callback introspection, DRF `reverse_action()`, hyperlink fields, and schema generation; verify that `drf-spectacular` exports only the requested version plus unversioned routes when invoked with `--api-version`.
9. URLconf inclusion, application namespaces, and multiple router instances.
10. Lifecycle middleware identifies the selected route version and applies the correct deprecation/sunset policy.
11. Core package imports and Django-native routes work in an environment where DRF is not installed.
12. Full unit/integration/compatibility matrix, wheel build, installed-wheel smoke test, and website build.

## 9. Delivery gates

Implement in small reviewable steps:
1. Add this contract and agree the public API.
2. Add registry support for preserving complete URLPattern objects, with regression tests for existing decorator registrations.
3. Add the ViewSet router with failing integration tests for the complete route behavior.
4. Add exact-version reversal and the DRF request-version adapter.
5. Verify schema, lifecycle, URLconf inclusion, optional-dependency behavior, and the supported compatibility matrix.
6. Update README, canonical contract, reference, article corpus, and changelog only after the runtime behavior is verified.

Do not remove the README's ViewSet limitation or advertise the new integration until all acceptance tests pass. This design document alone does not justify a package release.
