# Consumer API migration: V1 → V2 → V3

This is a runnable consumer-side migration project, separate from the library's focused OpenAPI contract fixture. It demonstrates a realistic coexistence period, version-specific response contracts, inherited routes, explicit endpoint retirement, and the lifecycle of an old API version.

## Scenario

| Version | Order representation | Availability action | Legacy export action | New risk summary |
|---|---|---|---|---|
| V1 | `total` is a string | available | available | absent |
| V2 | `total` is decimal + `currency` | inherited unchanged | still available | absent |
| V3 | adds `fulfillment_state` | inherited unchanged | explicitly removed | available |

The router registers the three Order ViewSets in order. V2 and V3 replace list/detail behavior but deliberately do not redeclare the availability action, so it is inherited. The legacy export action remains available during V2's coexistence window and is removed starting at V3:

```python
router.remove("orders", "order-legacy-export", from_version=3)
```

V1 is deprecated with a future Sunset date. The runtime checks prove that it returns Deprecation and Sunset headers while the version remains available. A separate test overrides the Sunset date into the past and verifies the middleware returns 410 before the view executes.

## Run locally

From the repository root:

```bash
python -m pip install -e .
python -m pip install -r examples/consumer_migration/requirements.txt
python examples/consumer_migration/generate_schemas.py \
  --output-dir /tmp/consumer-migration-schemas
python examples/consumer_migration/verify.py \
  --schema-dir /tmp/consumer-migration-schemas
```

The project includes one OpenAPI baseline per version. Normal CI and local verification compare generated bytes against those snapshots and fail on unreviewed changes.

To update a snapshot intentionally, generate all three candidate schemas, inspect the diff for each version, update only the reviewed snapshots, then run verification again.

## Consumer migration sequence

1. **Publish V1.** Consumers integrate against the original string-valued `total` contract.
2. **Publish V2 alongside V1.** V2 adds `currency` and a decimal `total`; do not silently reinterpret the V1 field. Keep both versions live while clients migrate. The unchanged availability action is inherited, and the legacy export remains available.
3. **Announce V1 deprecation.** Publish the deprecation date and future Sunset date. Use the response headers and out-of-band client communication; headers alone are not a migration plan.
4. **Publish V3.** V3 adds `fulfillment_state`, adds the risk-summary action, and removes legacy export from V3. V1 and V2 remain available according to the published policy.
5. **Retire V1 after the migration window.** Once its Sunset date is in the past, the lifecycle middleware returns 410 for V1. The example uses a test override to prove this behavior without waiting for the actual date.

## Rollback constraints

- **Before V3 is published:** removing the `router.remove(..., from_version=3)` declaration restores the legacy action to V3's route set. Regenerate and review the V3 schema before release.
- **After V3 is published:** do not silently reintroduce the old action into V3. Clients may have integrated against its absence and the V3 schema. Prefer a new version or a separately reviewed compatibility route with an explicit contract.
- **After V1 retirement:** rolling back application code does not automatically make V1 safe to reactivate. Reopening it requires an explicit lifecycle-policy change, consumer communication, and confirmation that any removed backend behavior/data dependencies still exist.
- **Schema rollback is not data rollback.** OpenAPI snapshots describe the public contract; they do not reverse database migrations, event formats, or side effects.

## What this example proves—and what it does not

The runtime tests prove actual HTTP behavior for V1/V2/V3, inherited actions, removed actions, deprecation headers, and 410 retirement. The generated schemas prove the documented per-version route and serializer shapes. They do not prove that arbitrary business semantics are backward-compatible; those require domain-specific contract tests and production migration telemetry.

All framework and schema-generator versions are pinned in this example's `requirements.txt` so schema changes are deliberate and reproducible.
